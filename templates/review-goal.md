# Goal: 只读代码 Review — `<项目名>`

> 致 runner：本份只做只读审查，**不改一行代码**。做完即停，别顺手修。
> 配套调度先验见 `references/playbooks/review.md`（何时触发/用哪个 primitive/停止条件）。
> 本模版管「派工提示词怎么写」，playbook 管「什么时候派」。

## 权限边界（硬约束）

只允许读取和分析。**禁止**：修改文件、创建文件、删除文件、执行终端命令（只读命令如 `grep`/`rg`/`wc`/`cat`/`ls` 除外）、安装依赖、格式化代码、自动修复、提交代码。

违反任一条即本轮作废。

## 审查目标

找出影响**稳定性、安全性、可维护性、性能、扩展性**的真实问题。只报真实问题，不凑数、不提风格意见。

## 审查维度（按维度分派子代理并行）

| 维度 | 重点 | 建议 agent |
|---|---|---|
| 1. bug 与错误处理 | 非测试路径 panic、错误被静默吞、UTF-8 字节切分、serde 默认值陷阱、边界条件 | `<lang>-reviewer` |
| 2. 安全 | 命令注入、路径穿越、密钥泄漏、env 透传、文件权限、插件/外部调用信任边界 | `security-reviewer` |
| 3. 架构 | 巨型文件/函数、模块边界、循环依赖、代码重复、扩展改动面 | `architect` |
| 4. 异步与状态 | 阻塞调用在 async 上下文、子进程回收、超时后状态一致性、文件锁、落盘原子性与顺序、cancel safety | `<lang>-reviewer` |
| 5. 测试 | 零测试模块、高风险模块覆盖率、集成测试实际覆盖面、`#[ignore]`、测实现 vs 测行为 | `general-purpose` |
| 6. 性能与依赖 | 热路径重复计算、全量重读解析、O(n²)、env 变量清单与缺失行为、构建配置、平台假设、产物增长治理 | `general-purpose` |

## 输出格式

1. 项目整体评价（含**已做对的**，用实证支撑，不只列问题）
2. 最严重的 5 个问题（表格）
3. 按 Critical / High / Medium / Low 分类列出**全部**问题
4. 每个问题必须包含：
   - a. 文件位置（精确到 `文件:行号`）
   - b. 问题描述
   - c. 影响范围
   - d. 触发场景
   - e. 修改建议
   - f. 是否建议立刻修复
5. 已核查并**排除**的假问题清单（避免后续 review 重复劳动）
6. 修复优先级分组（立刻修 / 近期排入 / 下次大改前）

缺上下文的判断标注「需要进一步确认」，不要猜。

## 质量闸门（写进 goal，防常见翻车）

以下每条都源自实战翻车，不是套话：

1. **子代理的定级结论必须核对其前提事实**。定级依赖的事实前提（"该函数无生产调用方"、"某机制已兜底此路径"）往往一条命令即可证伪。直接采信会漏掉最严重的问题。
2. **测试计数不能只靠 `rg -c "#[test]"`**。`#[path = "xxx_tests.rs"]` 外挂的测试模块会被计成 0，造成"零测试"误判。先跑 `rg -n '#\[path' src` 确认口径。
3. **排除某类问题时要追进函数内部**。例如查"async 中的阻塞调用"，只看调用点的 `Command` 类型不够，被调函数内部可能是同步子进程。
4. **同名不同路径的机制不能混为一谈**。例如脱敏名单只作用于 JSON 键遍历时，对"裸字符串写文件"无效。确认机制的**实际生效路径**。
5. **测试断言里的字符串不算硬编码问题**。grep 命中后先看是否在 `#[cfg(test)]` 内。
6. **报告要含"已排除的假问题"**。否则下一轮 review 会重复排查同样的嫌疑点。
7. **"文件太大"要扣掉测试再判**。`wc -l` 含 `#[cfg(test)] mod tests`，一个 6653 行的文件可能实际代码只有 4150 行。先 `rg -n '^#\[cfg\(test\)\]'` 定位测试起点。
8. **性能问题要给实测数字**，不接受"每次全量重读所以慢"。测出单次耗时与它所在循环的间隔，算出占比。占比低于 1% 的不是问题。

## 完成判据

- 六个维度全部有结论（含"未发现问题"也要明说）
- 每条问题都有 `文件:行号` 实证，不接受"某处可能存在"
- 已排除清单非空
- 全程无写操作：`git status` 应为干净（若在 git 仓）

## 派工侧注意（host 用，非 runner 的活）

这份模版派出去之前，host 先做完下面几件事，否则 runner 会卡在做不到的判据上：

1. **先确认 runner 有没有对应权限**。codex 等外部 runner 的会话策略常禁 git 写（`approval policy is Never`）。若判据里写了「commit」「push」，先验证权限；验不了就明写「代码与验证归 runner，commit 归 host」。
2. **派工前取基线**，不是派工后。runner 一动手，`rg -c` 之类的 instrument 基线就失真，事后无法区分"本来就没有"和"已被改掉"。
3. **审计要有 task 对象**。`lto audit` 的 brief 取自 `high_risk_tasks(&state)`，交付契约的 `--target` 不是 task。只写 target 不建 task，审计会拿到一份 `## Audit Targets` 为空的 brief，runner 无从下手。派工前先 `lto task add`。
4. **亲验要在干净负载下做**。与 runner 的审计/测试同机争抢 CPU 时，超时类断言会假红，容易冤枉 runner「虚报」。判定缺陷前先确认环境没被自己污染；必要时用 `git stash` 退回基线做对照组。
5. **runner 报阻塞时先读它的记录**。`lto task` 的 note 和它自建的进度文件通常写清了真因，别先入为主判它失职。
6. **上一轮遗留的 P2/待办清单不是缺陷列表**。那些条目是 review 时顺手记的"以后可以做"，从没被复查过，却会被下一轮当既定事实继承。派工修它们之前，先对每项跑一条能证伪它的命令（测规模 / 测耗时 / 数函数 / 找 bug 实例）。测不出收益的，摆数据请用户裁决要不要做——别默默执行完，也别自己划掉。

## 交付

一份 Markdown 报告。不创建其他文件，不修改代码。
